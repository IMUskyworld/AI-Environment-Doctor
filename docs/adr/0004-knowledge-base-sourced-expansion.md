# ADR 0004：知识库按官方来源扩充，判定语义分「可能」与「保证」

- 状态：已采纳（2026-10-20）
- 背景：v0.1.0 的知识库只覆盖 7 条生态规则与 CUDA 11.8–12.6 的驱动矩阵，
  而真实项目里最常见的两个盲区是：
  （a）**包自己的构建钉住了某个 CUDA runtime**（onnxruntime-gpu 1.21+ 用 CUDA 12.8、
  1.27+ 用 CUDA 13.0），项目文件里通常根本没提 CUDA，真实驱动要求对扫描不可见；
  （b）**版本区间型的 ABI 冲突**（NumPy 2.x vs torch < 2.3；cuDNN 8 vs 9），
  靠「包在不在」判断不出来，必须看版本约束的方向。
- 决策：
  1. 新增数据文件 `compat/data/package_cuda_requirements.json`，把「包 → 版本门槛 → CUDA runtime」
     变成数据；新增内置判定 `package_cuda_<包名>`，与驱动矩阵交叉验证；
  2. 条件 DSL 明确区分两组语义：
     - **可能**（`lib_may_install_below` / `lib_may_install_at_or_above`）：未固定版本 ⇒ 成立（风险成立）；
     - **保证**（`lib_pinned_below` / `lib_requires_at_least`）：未固定版本 ⇒ 不成立。
     「可能」用于「未固定就危险」的场景，「保证」用于「确实会发生」的场景；
  3. 驱动矩阵按 NVIDIA 官方发布说明的 GA 行重校（11.8 Windows 520.06、12.3 Windows 545.84、
     补齐 12.7/12.8/12.9/13.0），推导出来的行必须写 `note` 说明推导方式；
  4. 新增规则必须带官方来源链接 + 修复动作 + 单元测试，验收脚本 §22-13 强制检查。
- 理由：
  - 判定要能**回溯到官方文档**，否则用户凭什么信你给出的驱动版本号；
  - 「可能」与「保证」混用会把结论说反（未固定 ≠ 固定在旧版），这是规则库最容易出错的点，
    必须在 DSL 层面就区分开，而不是靠写规则的人自觉；
  - 数据与代码分离：NVIDIA 更新驱动表、ONNX Runtime 更新版本对照表时，只改 JSON。
- 代价：条件 DSL 多两个 kind（需要写清楚它们的区别，见 CONTRIBUTING.md 与 DEVELOPMENT.md §11.3）；
  规则库变长（11 条），维护成本上升——用「每条规则都要有来源与测试」来兜住。
- 触发复议的条件：出现需要表达更复杂版本约束（如 `~=`, `!=`, 交集）才能描述的常见冲突。
