# ADR 0005：Web 控制台用标准库实现，且默认只监听回环地址

- 状态：已采纳（2026-10-20）
- 背景：envdoctor 原本只有 CLI。实际使用中两类诉求很常见：
  （a）不想在终端里来回翻长输出；（b）想把诊断结果直接发给同事。
  报告本来就是自包含 HTML，缺的是「一个能点的地方」。
- 决策：
  1. 新增 `envdoctor web` 子命令：**只用 Python 标准库**（`http.server`）实现服务端，
     前端是**单文件自包含**的内联 CSS/JS（无 CDN、无构建步骤、无外部资源）；
  2. **不新增任何运行时依赖**；
  3. Web 与 CLI **共用同一套流水线与产物协议**（同一份 `scan/probe/verdicts/verify/report`
     落在同一个 `.envdoctor/runs/`），报告只有一份真相；
  4. 安全模型比 CLI 更严：默认只监听 `127.0.0.1`、每次启动生成一次性令牌、
     `Host` 头必须回环（防 DNS rebinding）、写操作必须同源、真实验证必须显式勾选同意；
  5. 后台任务用「线程 + 状态机」实现，不引入队列与持久化。
- 理由：
  - 引入 Web 框架（FastAPI/Starlette + uvicorn）会给一个「装到哪都能用」的工具加上
    一堆传递依赖与版本约束，收益不匹配；标准库足够写一个本地单用户控制台；
  - 前端自包含与 `report.html` 同一原则：离线可开、无外部请求、无遥测；
  - 这个进程有能力**安装并执行第三方代码**，所以「谁能触发它」必须按最坏情况设计：
    假设本机有恶意网页会尝试访问 localhost。
- 代价：
  - 标准库的 HTTP 服务没有异步与中间件，路由、同源校验、令牌校验都要自己写（约 200 行）；
  - 只支持单用户本地使用，不做鉴权、多用户、任务持久化（刻意不做）；
  - 前端是手写 vanilla JS，没有组件化与类型检查。
- 触发复议的条件：需要多用户/远程部署（那时应换真正的 Web 框架并补鉴权），
  或需要任务队列与断点续跑。
